运行环境驱动的信任边界模型 v0.2

日期：2026-10-26。状态：待实例化的边界模型。

本轮修正

v0.1 中 B1–B10 主要描述功能接口和信息流，不能直接作为实际信任边界的清单。本轮优先识别运行环境中的保护域、身份、控制主体和执行机制。既有风险清单仍保留为假设，暂不扩展或评分。

计算机、服务器、物联网设备是场景分类，不能单凭设备名称判断隔离强弱。例如，同一账号下的服务器进程可能共享权限；Linux 物联网网关与无内存保护的单地址空间固件则应使用不同模型。

1. 一条边界到底描述什么

用五部分描述：域 A / 域 B / 跨界能力 / 判定依据 / 强制执行者。

这里的“域”是具有明确身份、权限或控制主体的一组实体，不一定是单独机器。记录三个不同层面：

  • 权限隔离边界：例如受限工作负载与宿主。是否成立取决于实际权限和执行机制，不能由方框推断。
  • 管理与信任边界：例如本地应用与第三方模型服务。即使通信已加密，管理主体及数据责任仍发生变化。
  • 语义授权边界：例如文档内容与用户指令。同进程也存在信任差异，但它本身不阻止文件读取或命令执行。

同一个接口可以同时跨越以上多个层面。身份不同也不必然意味着已经隔离；仍需检查共享权限和可用旁路。

每条候选边界标记为：待验证 / 已验证执行 / 已知共享或缺口 / 不适用。缺少隔离时，应明确合并保护域，不能把不存在的隔离继续画成已实现防线。

2. 个人计算机：用户会话与应用权限

参考场景：Agent 以交互用户身份运行，可调用本地工具或操纵浏览器。以下全是待验证候选边界。

ID域 A → 域 B跨界能力与判定依据执行者及待核实项典型共享或缺口
PC1Agent 进程 → 用户文件与其他进程文件读写、进程访问；检查运行身份、目录授权和进程权限OS 与已配置的应用隔离；核实真实访问清单同用户可访问的资源可能直接暴露；独立进程不等于权限收敛
PC2网页脚本 → 本地浏览器自动化控制器DOM、下载、扩展或自动化接口；区分站点权限与控制器权限浏览器、扩展授权及本地控制接口；核实调试端口与配置控制器能操纵已登录会话，网页内容可诱导其使用更高权限
PC3Agent／应用 → 系统级权限提权、安装、系统配置、设备和辅助控制能力OS 授权与特权服务；核实是否已有持久授权用户预先授予的控制能力可能被所有任务复用
PC4本地应用 → 远程模型／工具服务上下文上传、API 调用；检查端点身份、账号权限和管理主体远程服务授权、传输与本地出口；核实实际发送内容本地沙箱不限制远程服务内部能做什么
PC5Agent／工具 → 登录会话与凭据存储获取或代用令牌、Cookie、密钥；区分读到秘密与借用会话凭据存储、浏览器及服务端；核实可导出性与调用权限不能读取密码也可能通过已登录页面完成操作

核心问题：Agent 到底拥有自己的受限身份，还是在借用整个人的桌面权限？

3. 服务器：工作负载、租户与管理面

参考场景：服务接收任务，在工作负载中运行 Agent 并访问业务系统。不能默认已容器化或已实现租户隔离。

ID域 A → 域 B跨界能力与判定依据执行者及待核实项典型共享或缺口
SV1请求／租户 A → 任务与租户 B 的资源请求、队列、缓存、数据查询；检查租户绑定与任务归属API、调度器和存储服务；核实每条路径是否校验租户多租户共用数据库账号时，数据隔离可能完全依赖应用逻辑
SV2Agent 工作负载 → 宿主与其他工作负载系统调用、挂载、运行时接口、网络访问OS、容器或虚拟机隔离；核实挂载、特权和资源配置容器名称不构成保证；共享宿主目录或管理接口可扩大权限
SV3工作负载身份 → 业务服务／云资源服务调用、数据访问、角色委派目标服务授权与身份系统；核实实际凭据和资源范围网络可达不代表获准访问；过宽服务身份使合法接口产生大范围影响
SV4任务数据面 → 管理控制面修改部署、策略、密钥、镜像或运行配置管理 API、运维身份与部署流程；核实任务能否获得管理凭据工作负载接触编排或管理接口时，可能改变自身约束
SV5异步任务／重试 → 持久状态和副作用消息消费、结果提交、任务恢复；检查身份、租户及操作绑定队列消费者、状态服务与业务端；核实重放、取消及幂等队列不是天然权限边界；重试可能沿用过期授权或重复操作

核心问题：任务、租户、工作负载与服务身份是否真实分离，还是共同借用一个高权限服务账号？

4. 物联网：先按执行能力分型

4.1 有 OS 的边缘设备或网关

ID域 A → 域 B跨界能力与判定依据执行者及待核实项典型共享或缺口
IO1Agent 进程 → 设备驱动与设备节点总线、串口、GPIO、驱动调用；检查进程身份与设备访问权OS、驱动与设备代理；核实是否直接暴露设备接口进程隔离不限制已获准的危险设备指令
IO2云端控制主体 → 设备本地控制域远程任务、指令、配置；检查设备身份、指令权限与时效设备端校验和本地控制逻辑；核实离线行为及授权缓存认证连接不能证明每条指令符合本地安全条件
IO3本地网络／维护方 → 设备管理域配置、更新、调试和远程维护设备管理与更新机制；核实维护入口和恢复路径维护账号与业务进程可能共享高权限

4.2 MCU／RTOS／单地址空间设备

ID域 A → 域 B跨界能力与判定依据执行者及待核实项典型共享或缺口
MC1Agent／推理任务 → 固件其他任务与内存内存访问、调度、外设寄存器；检查硬件保护与任务权限配置仅在存在并启用相应保护机制时成立无有效内存或权限隔离时，应合并为一个保护域，不能画独立沙箱
MC2网络处理／外部指令 → 控制循环指令解析、状态切换、执行调度固件中的校验与控制状态机；核实是否能被其他路径直接调用同地址空间中的软件校验通常与固件共用失陷范围
MC3更新／调试接口 → 固件与设备密钥烧录、调试、恢复、密钥访问启动、更新与硬件访问机制；核实实际配置及恢复策略物理可接触不等于已控制设备，但暴露接口必须单独建模

4.3 两类设备都要检查的物理边界

ID域 A → 域 B跨界能力与判定依据执行者及待核实项典型共享或缺口
PH1物理环境 → 传感与状态估计测量、时序、校准；检查数据来源与物理假设传感器、采集链路及交叉校验；核实环境干扰传感器身份真实不意味着读数反映真实状态
PH2软件控制 → 执行器与物理过程电机、阀门、加热等；检查动作范围及过程状态本地限值或独立保护；必须核实是否独立及其故障模式若保护与 Agent 共享同一固件或电源，不能直接假定失陷后仍有效

核心问题：设备有没有可独立执行的保护域？如果没有，安全保证最终由哪一层承担？

5. 跨环境组合与覆盖检查

云端 Agent 控制设备时，应把 SV3、IO2／MC2 和 PH2 串成一条路径；云端身份授权与设备侧动作约束分别检查。不能把“调用设备 API 成功”当成物理动作安全。

三类部署还必须覆盖：第三方模型与工具服务、更新来源、凭据、数据存储、日志和备份。这些不是服务器或物联网专属项，应按实际位置和管理主体加边界。本页表格是参考场景的起点，不是穷尽目录。

6. 下一轮只做边界实例化

对一个具体系统填写：

  1. Agent、模型、工具分别在哪台设备、哪个进程或固件任务运行？
  2. 每个实体使用什么 OS 身份、服务身份和业务身份？
  3. 哪些实体共享内存、文件、凭据、设备或管理接口？
  4. 每条跨域操作由谁判定、谁执行？是否存在 Shell、直接网络等旁路？
  5. 判定者被攻陷、断网或重启后，约束还成立吗？

输出一张实际域图和一张边界表，标明证据与未知项。边界稳定之后，再把旧 B 编号映射到实际边界并重建风险路径；当前不批量改写风险编号，以免制造虚假的精确性。
