沿原架构图补充边界说明 v0.3

日期：2026-10-26。参考：WorkBuddy 终端安全方案全景原图。

本文保留原图的三层组织方式和 Agent Loop 六个阶段。新增内容是研究建议，原图中未说明的实现能力一律待验证，不能据图认定已有强制执行能力。环境边界编号来自 v0.2。

1. 外层：终端与网络防护

原图节点要补画的两侧边界运行环境差异必须核实的执行与覆盖条件
EDR：文件／进程行为监控Agent／工具进程 ↔ 用户资源、宿主与特权域PC1/PC3：交互用户权限；SV2/SV4：工作负载和管理面；IO1/MC1：设备接口及内存保护能力产品是否支持该环境？是告警还是可阻断？共享权限下能看到什么，漏掉什么？不能把监控视作隔离
零信任网关：资源访问入口本地执行主体 ↔ 远程模型、工具和业务服务PC4：桌面应用出口；SV3：服务身份与目标资源；IO2：云设备通信；MCU需检查实际通信栈或网关是否所有调用经过网关？Shell、浏览器、直接网络是否可旁路？目标服务是否独立做授权？加密认证不能替代动作授权
EDLP：办公通道外发管控可访问数据的主体 ↔ 接收方及外发通道PC5：浏览器会话和办公应用；SV1/SV3：租户及服务出口；物联网另需识别遥测、消息和设备协议覆盖 IM、邮件等不代表覆盖模型请求、工具结果、日志、遥测和自定义 API。需枚举实际出口

新增：在该层旁边标注“可接入既有安全能力”，并明确每项覆盖范围及失效行为。没有部署相应软件时，不能声称仍有同等防护；应列出基础部署尚存的缺口，以及是否有其他机制承担相应要求。

2. 中层：执行边界与准入

原图节点要补画的边界环境映射与关键补充
File / Net / Cmd Sandbox不可信或受限执行主体 ↔ 文件、网络、进程、设备及宿主PC1/PC3：用户权限与特权服务；SV2：挂载、管理接口和工作负载；IO1：设备节点；MC1：无有效内存保护时不能假定沙箱存在。需要标注实际隔离执行者、授权范围和旁路
Skill 准入发布者／制品来源 ↔ 安装与执行域签名、扫描、SBOM等回答来源与制品问题；还要把安装时身份和运行时权限分开。不同Skill若共用同一高权限进程，准入不提供彼此隔离
Agent 准入接入主体 ↔ 可使用的企业资源与任务权限PC：绑定用户与会话；服务器：绑定租户、任务、服务身份；设备：绑定设备、远程控制主体和本地维护身份。准入通过不应自动获得所有资源权限

新增横向区域：身份与授权管理面。标注谁签发权限、谁能修改策略、谁能更新Skill、如何吊销及终止任务。它关联各层，但不应直接暴露给任务执行身份。

3. 内层：数据防泄漏与运行时拦截

保留原图的数据与凭据防泄漏插件、运行时风险拦截插件。补充四项契约：

  1. 检测契约：输入是什么、输出是什么、误判与漏判如何处置。语义判断本身不构成资源隔离。
  2. 执行契约：由哪个工具服务、代理、OS或业务端强制执行判定？模型或Skill能否绕过？
  3. 授权契约：授权绑定哪个主体、任务、对象、动作、期限和参数？需要确认时，确认的是否是实际执行内容？
  4. 失效契约：插件不可用、超时、断网或重启后，哪些操作暂停，哪些继续？设备侧不能直接套用统一停止策略，要考虑安全状态。

这些阶段是检查位置，不能按“六个阶段都有插件”推导出全部跨界路径都被覆盖。

4. 沿原图新增的三个标注区

  • 环境底座：PC用户会话／服务器工作负载与租户／有OS设备／单地址空间固件，标明实际隔离机制及不存在的边界。
  • 管理与信任基础：管理者、策略、凭据、更新和审计。需明确哪些主体被信任；宿主或管理面失陷后的保证另行定义。
  • 设备感知与物理执行：PH1传感真实性、PH2动作约束与保护机制，补足原终端图未展开的物理侧边界。

5. 用一个跨层场景检查原图

示例：Agent 读取外部文档，被诱导上传用户文件。

  1. 文档进入上下文：内层插件可能检测指令注入，但需评估漏判。
  2. 形成上传请求：运行时校验任务授权与目标，而非仅检查文字是否可疑。
  3. 工具读取文件：中层执行边界限制可访问文件，环境权限决定能否越界。
  4. 上传外部目标：出口和远程资源授权约束实际发送；现有网关／DLP是否覆盖该路径需验证。
  5. 各层关联同一任务、授权及执行事件，才能定位漏过哪一环。

该示例不证明多层一定有效，而是用于逐层检查执行者和旁路。下一步应选择原图中的一个节点，例如工具执行，从PC、服务器、两类设备分别画出真实边界，再回到风险路径。
